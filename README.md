# Koin DI Navigation

Плагин для IntelliJ IDEA **2026.3 (ветка 263, build 263.7307.200)** с Kotlin K2. Добавляет переходы между регистрациями Koin и местами получения зависимостей, включая обёртки над DI-вызовами в исходниках проекта.

## Установка и работа

1. Скачайте ZIP из [GitHub Releases](https://github.com/InsanusMokrassar/PluginsDIIdiaHighlight/releases/latest) или соберите `build/distributions/PluginsDIIdiaHighlight-1.0.3.zip` командой ниже.
2. В IDEA откройте **Settings → Plugins → ⚙ → Install Plugin from Disk**, выберите ZIP и перезапустите IDE.
3. Откройте Kotlin-проект, выполните Gradle Sync и дождитесь индексации IDEA, затем фоновой задачи **Indexing Koin DI navigation**. Значки появятся после подготовки кэша.
4. Синий значок слева от `single` / `factory` ведёт к получениям зависимости. Зелёный значок слева от `get` / `getOrNull` ведёт к регистрациям. Один результат открывается сразу; несколько — в списке с именем файла и строкой. При отсутствии результата появляется подсказка.

Значки можно отключить в **Settings → Editor → General → Gutter Icons → Koin DI navigation**.

Для обновления с предыдущей версии установите новый ZIP тем же способом: идентификатор плагина сохранён. После открытия проекта в IDEA кэш подготовится автоматически.

## Что распознаётся

- Koin: `single`, `factory`, `scoped`, `singleOf`, `factoryOf`, `scopedOf`; `get`, `getOrNull`, `getAll`, `inject`, `injectOrNull` у Koin/Scope/KoinComponent; `koinInject` из Koin Compose.
- Выведенные Kotlin-типы: `single { Service() }`, `Consumer(get())`; import aliases и полные имена.
- Прямые обёртки в исходниках проекта: функция с expression body или единственным `return` и свойства с таким getter. Например, `fun Koin.service(): Api = get<Service>()`. Ключ зависимости берётся из вложенного DI-вызова: в этом примере это `Service`, даже если обёртка возвращает `Api`.
- Цепочки обёрток до шести уровней, включая generic-параметры с любыми именами, import aliases и обёртки над расширениями библиотек. Учитываются также `named` / `bind` из options-блока возвращаемого вызова.
- `bind` / `binds`, известные строковые и типовые qualifiers, ссылки на неизменяемые свойства с qualifiers. `getAll` учитывает также регистрации со случайными qualifiers.

Для бинарных расширений без исходников предусмотрены отдельные адаптеры. Адаптер MicroUtils распознаёт `singleWithBinds`, `factoryWithBinds`, варианты `WithRandomQualifier` / `WithRandomQualifierAndBinds`, `singleSuspend`, `factorySuspend`, строковые qualifiers, `getAllDistinct`, `getAny` и `lazyInject`. Он применяется только к разрешённым символам этой библиотеки, в том числе полученным через транзитивные зависимости. Обёртки над этими операциями распознаются тем же анализом цепочек; сами библиотеки в плагин не включаются.

Вызовы определяются по разрешённым Kotlin-символам. Обычные `List.single()`, `Map.get()`, `Result.getOrNull()` и `ParametersHolder.get()` не считаются получением DI.

## Границы статического анализа

Поиск показывает **кандидатов во всех исходниках проекта**, включая другие модули и source sets: регистрация может находиться в приложении, зависящем от модуля с `get()`. Плагин не исполняет код проекта, не определяет активный Koin-контейнер, scope, условия регистрации, порядок overrides или конфигурацию конкретного запуска. Поэтому несколько регистраций — ожидаемый результат.

Koin использует ключ класса (`KClass`) и qualifier, стирая аргументы generic-типа. Поэтому `List<String>` и `List<Int>` с одинаковым qualifier являются кандидатами друг для друга; полный выведенный тип отображается в подсказке. `get<Lazy<Service>>()` остаётся поиском `Lazy`, а `inject<Service>()` — поиском `Service`.

Динамический qualifier сопоставляется только при общей статически распознаваемой ссылке. Вычисляемые значения, изменяемые переменные, произвольный control flow и reflection не интерпретируются. Произвольные обёртки распознаются только в исходниках проекта, включая generated source roots. Анализ не восстанавливает произвольную реализацию из байткода: для неизвестного бинарного DSL нужен отдельный адаптер. Встроенные операции Koin и поддерживаемые адаптеры работают без attached sources. Цели переходов — исходники проекта.

Для `WithBinds` адаптер добавляет supertypes только при стандартном `bindFilter`; переданный фильтр не исполняется. `getAllDistinct` / `getAny` учитывают регистрации со случайными qualifiers.

## Сборка и тесты

Нужен **JDK 25**. Gradle Wrapper 9.5.0 включён. По умолчанию сборка загружает IDEA 2026.3; можно использовать уже установленную IDE той же версии:

```bash
IDEA_PATH=/path/to/intellij-idea
JAVA_HOME="$IDEA_PATH/jbr" ./gradlew test verifyPluginStructure buildPlugin \
  -PlocalIdePath="$IDEA_PATH"
```

ZIP появится в `build/distributions/`. Для отдельного экземпляра IDE с плагином:

```bash
JAVA_HOME="$IDEA_PATH/jbr" ./gradlew runIde -PlocalIdePath="$IDEA_PATH"
```

Проверка бинарной совместимости с выбранной IDE: `./gradlew verifyPlugin -PlocalIdePath="$IDEA_PATH"` (также с JDK 25). Verifier использует bundled-зависимости выбранной IDE в offline-режиме. Диапазон совместимости намеренно ограничен веткой 263 из-за изменений Kotlin Analysis API; рекомендация Gradle удалить `until-build` здесь не применяется. Для IDEA 2026.2 остаётся предыдущий релиз плагина.

Тесты используют IntelliJ fixtures, настоящий K2 Analysis API, Koin **4.2.2** и MicroUtils **0.30.1** для проверки адаптера. Проверяются оба направления переходов, выведенные типы, qualifiers, bindings, обёртки/свойства, цепочки generic-обёрток с расширенным возвращаемым типом, HTML-экранирование подсказок и отсутствие ложных маркеров у обычных Kotlin API. Отдельные проверки покрывают повторные переходы без Kotlin-анализа, обновление кэша после правок, изменение обёртки в другом файле, отмену подготовки и настоящий фоновый обработчик с UI callbacks. HTML-отчёт: `build/reports/tests/test/index.html`.

## Автоматическая сборка и публикация

Workflow **Package plugin** запускается при каждом push в основную ветку `main` и вручную через **Actions → Package plugin → Run workflow**. Он выполняет тесты, проверку структуры и совместимости, затем собирает установочный ZIP. Версия берётся из `plugin.xml` внутри готового архива, исходное значение задаётся в `build.gradle.kts`.

Архив сохраняется как Actions artifact на 14 дней и публикуется в GitHub Release с тегом `v<версия>`, например `v1.0.3`. Теги и опубликованные архивы не заменяются. Повторный запуск для того же коммита скачивает существующий ZIP и сравнивает SHA-256; при совпадении публикация пропускается. Другой коммит или другие байты требуют новой версии в `build.gradle.kts`. Незавершённый draft того же коммита можно завершить, если его архив отсутствует либо совпадает с текущим; конфликтующие или повреждённые assets не перезаписываются.

При ошибке workflow сохраняет доступные отчёты тестов и Plugin Verifier в артефакте `verification-reports-<run>-<attempt>` на 7 дней. Их можно скачать со страницы соответствующего запуска в Actions.

Публикации выполняются последовательно. Повторный запуск старого коммита сохранит Actions artifact, но пропустит Release, если `main` уже указывает на другой коммит. Используется штатный `GITHUB_TOKEN` с `contents: write`; отдельный PAT не нужен. Доступность релизов определяется настройками репозитория. Защиту от замены со стороны GitHub можно дополнительно включить настройкой immutable releases; workflow совместим с ней.

Защитные сценарии публикации проверяются без обращения к GitHub: `python3 -m unittest discover -s .github/scripts -p 'test_publish_release.py'`. Gradle Wrapper проверяет SHA-256 загружаемого дистрибутива.

## Индексация и производительность

С версии **1.0.1** анализ проекта вынесен из обработчика клика. Встроенный `FileBasedIndex` IDEA сохраняет синтаксические имена вызовов, алиасы и прямые обёртки вместе с обычной индексацией. После готовности индексов плагин в фоне разрешает Kotlin-символы в файлах-кандидатах и собирает таблицы регистраций и получений по типу зависимости. Клик ищет результат в этих таблицах. `ast-index` для работы плагина не требуется.

Семантический кэш хранится в памяти проекта и заново готовится после открытия проекта в IDEA. Первичная подготовка большого проекта занимает время; её состояние видно в фоновых задачах IDEA. Правки объединяются с задержкой 250 мс. Уже обработанные файлы сохраняются при прерывании анализа записью; обычная правка тела функции обновляет затронутые файлы. Кэш также отслеживает исходники используемых обёрток и qualifiers, включая превращение обычной функции в DI-обёртку. Изменения объявлений, состава обёрток или корней проекта могут потребовать полной фоновой перепроверки.

Если нажать на существующий значок во время обновления, появится подсказка, а переход выполнится после готовности кэша. Разрешение Kotlin-символов и обход проекта выполняются вне EDT. Подписи списка переходов готовятся заранее и не обращаются к PSI из Swing renderer.

В тестовом стенде на 200 файлах / 1 800 DI-точках проверяются 100 повторных запросов без повторного анализа файлов и сохранение кэша после правки посторонней функции. Этот тест не является замером задержки на реальном пользовательском проекте.

API-основание: [IntelliJ line markers](https://plugins.jetbrains.com/docs/intellij/line-marker-provider.html), [IntelliJ Platform Gradle Plugin](https://plugins.jetbrains.com/docs/intellij/tools-intellij-platform-gradle-plugin.html), [Kotlin Analysis API](https://kotlin.github.io/analysis-api/).
